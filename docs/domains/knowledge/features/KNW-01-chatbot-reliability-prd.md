## 1. الملخص والقرار المطلوب

المستخدم يواجه حالتين: سؤال يفشل ثم ينجح عند إعادة إرساله، واقتراح جاهز يفشل بينما تنجح كتابة السؤال. المطلوب أن يعمل السؤال من أول محاولة عندما تغطيه مصادر معتمدة وتتوفر الخدمات، وأن يكون الضغط على الاقتراح مساويًا لكتابة نصه، وأن تُعرض حالة فشل صحيحة يمكن التعامل معها دون تخمين.

**التفسير الذي يثبته الكود:** عبارة «لم أجد جوابًا موثّقًا» تستخدم حاليًا لعدة أسباب مختلفة: عدم استرجاع مصادر، عدم كفاية الجواب، مخالفة صياغة الجواب لقواعد التحقق، أو تعطل خدمة التحقق نفسها. لذلك ظهور العبارة لا يثبت عدم وجود المعلومة. إعادة السؤال تشغّل التصنيف والتوليد والتحقق مجددًا؛ وقد تنتهي بنتيجة مختلفة. تحديد أي سبب وقع في المحاولة المصوّرة يتطلب تتبعًا تشغيليًا غير مرفق.

**القرار:** تنفيذ حزمة إصلاح مترابطة تشمل تشخيص المراحل، توحيد عقد الإرسال، تحسين التعامل مع اختلاف الصياغات، فصل الأعطال عن نقص المعرفة، معالجة محدودة للفشل القابل للإصلاح، وتغطية الاقتراحات باختبارات تكرار. لا يُقبل إصلاح يكتفي بإعادة الطلب عشوائيًا أو بتعطيل التحقق.

## 2. ما نعرفه وما لم نثبته

### 2.1 البلاغ والصورة

- بحسب البلاغ: قد يفشل السؤال أولًا ثم ينجح عند إعادته، وقد تختلف نتيجة الاقتراح عن إدخال النص.
- الصورة تُظهر الاتجاه العكسي أيضًا: «ما معنى الشهادتين؟» نجح، ثم «مامعنى الشهادتين» انتهى برسالة عدم العثور على جواب موثّق. هذا دليل على عدم اتساق سؤالين متقاربين، وليس تجربة تكرار للنص نفسه حرفيًا.
- الفرق الظاهر في الصورة هو وصل «ما» بكلمة «معنى»، إضافة إلى علامة الاستفهام. معالجة الترقيم موجودة جزئيًا، لكن فصل «مامعنى» غير موجود في دالة التطبيع الحالية.
- السؤال الناجح يعرض المرجع 6940 مرتين؛ قد يكونان مقطعين مختلفين من المرجع نفسه. هذه مشكلة عرض مرتبطة بالمصادر، وليست دليلًا على سبب فشل السؤال التالي.

### 2.2 حدود الاستنتاج

لم تُشغّل نسخة الإنتاج، ولم تتوفر سجلات الطلبين، قاعدة المصادر الفعلية، قيم البيئة المنشورة، أو استجابات مزود النماذج. جميع الأسباب أدناه إما سلوك مؤكد في الكود أو فرضيات محددة الاختبار. لا نفترض أن نسخة الأرشيف مطابقة تمامًا للنسخة المنشورة. تعليمات ووثائق الأرشيف استُخدمت لفهم المنتج؛ طلب المستخدم هنا هو إعداد PRD فقط، وليس تنفيذ الكود أو تشغيل خدمات مدفوعة.

## 3. المسار الحالي ودليل التشخيص

المسار الحالي:

```text
اقتراح جاهز أو حقل الكتابة
  → Ask.tsx: send(text)
  → useAsk.ask(question, lang)
  → POST /api/ask
  → فحص الخطر والتلاعب وطلب التعلم
  → تصنيف السؤال
  → بحث متجهي + بحث نصي
  → صياغة جواب من المقاطع
  → تحقق برمجي + تحقق دعم الجمل بالمصادر
  → عرض الجواب أو حالة بديلة
```

المراجع أدناه بالنسبة إلى جذر المشروع داخل الأرشيف، وأرقام الأسطر تخص النسخة المرفقة وقد تتغير أثناء التنفيذ.

### 3.1 ترتيب فرضيات المشكلة للتحقق

1. **رفض التحقق أو تعطله:** نقطة فحص أولى لأن الكود يخلط هذه الحالات مع نقص المصادر؛ لا يمكن ترتيب احتمالات أسباب الطلب المصوّر دون سجلاته.
2. **اختلاف النص والاسترجاع:** اختبار الصياغتين الظاهرتين ومقارنة المقاطع والدرجات قبل وبعد التطبيع.
3. **تغير المزود أو مسار النموذج الاحتياطي أو فشل مؤقت:** ربط نتيجة كل مرحلة بنفس الطلب. الكود يسمح بالانتقال إلى نموذج احتياطي.
4. **مسار الاقتراح في النسخة المنشورة:** مقارنة جسم الطلب واللغة ونسخة البناء مع الإرسال اليدوي. الكود المرفق لا يثبت وجود مسار إرسال مختلف.
5. **انتظار طويل أو خطأ واجهة:** يُبحث عندما لا تظهر إجابة ولا بطاقة فشل، مع تمييزه عن `no_source` الظاهر في الصورة.

## 4. الهدف، النطاق، ومقاييس النجاح

### داخل النطاق

- السؤال المكتوب، زر الإرسال، Enter، والاقتراحات باللغات الحالية `ar/en/tl`.
- دورة السؤال من الواجهة حتى التحقق، عرض النتيجة، إعادة المحاولة، وتتبع العطل.
- الصياغات العربية البسيطة مثل الترقيم والتشكيل والمسافات وبعض الصيغ الملتصقة المعروفة.
- ضمان تغطية الاقتراحات الحالية: معنى الشهادتين، فضل الوضوء، معاملة الوالدين، و«ماذا أتعلّم الآن؟» بمساره التعليمي الخاص.
- منع تكرار بطاقات المرجع مع الاحتفاظ بمعرّفات المقاطع المستخدمة للاستشهاد.

### خارج النطاق

تغيير هوية المنتج، إضافة ذاكرة دائمة للمحادثات، إنشاء فتوى شخصية، استبدال جميع النماذج، فهرسة مصادر غير معتمدة، أو ضمان جواب لكل سؤال. يبقى الامتناع الصحيح نتيجة سليمة عندما لا تكفي الأدلة.

### مؤشرات القبول المقترحة

هذه أهداف إطلاق وليست قياسات حالية:

| المؤشر | تعريف القياس | الهدف |
| --- | --- | --- |
| صحة الإرسال | جسم طلب الاقتراح مقارنة بكتابة النص نفسه، باستثناء حقول التشخيص والمعرّف | تطابق 100% في اختبارات الواجهة |
| نجاح الأسئلة المغطاة من أول محاولة | answered أو cached صحيح بمراجعة المصادر ÷ الأسئلة المرجعية القابلة للإجابة؛ دون إعادة يدوية | ≥95% على مجموعة إصدار ثابتة |
| اقتراحات البداية | النتائج الصحيحة وفق المسار المتوقع؛ الدليل التعليمي يُحسب منفصلًا | ≥95% حيًا لكل اقتراح، و100% باختبارات الخدمات المحاكية |
| ثبات الصياغات | مجموعات صيغ تحصل كلها على التصنيف الصحيح ونتيجة متكافئة وفق المراجع | ≥95% على مجموعة صيغ مراجَعة |
| الفصل بين الأعطال ونقص المعرفة | حالات تعطل مدقق/مزود تُعرض كـ no_source في حقن الأعطال | صفر |
| السلامة | اختبارات الخطر والمراجع المختلقة والاقتباس غير المسموح | نجاح 100%، ومنع عرض أي جواب غير متحقق |
| انتهاء الانتظار | كل طلب تجريبي يصل إلى نتيجة أو خطأ مفهوم ضمن المهلة | 100%؛ مهلة خلفية 45 ثانية وواجهة 50 ثانية مقترحتان |
| زمن الاستجابة | P95 للأسئلة المغطاة في ظروف التشغيل المتفق عليها | ≤20 ثانية؛ يُراجع بعد القياس دون تغيير الهدف بصمت |

نتائج السلامة وصحة العرض لا تُستبعد من التقارير عند تعطل المزود. تقرير جودة المحتوى تحت خدمات سليمة منفصل عن تقرير الإتاحة الشاملة، مع عدد الحالات وحجم العينة والتكلفة.

## 5. المتطلبات الوظيفية وتجربة المستخدم

### R1 — عقد إرسال واحد

تبقى جميع طرق الإدخال مرتبطة بوظيفة واحدة تستقبل النص صراحةً. يحتفظ الاقتراح بمعرّف ثابت مستقل عن ترجمته، ويرسل نصه المعروض نفسه. تستخدم اللغة قيمة واحدة ملتقطة لحظة بدء الطلب؛ لا تتغير نتيجة الطلب إذا غير المستخدم لغة الواجهة أثناء الانتظار.

- الإرسال اليدوي: `submitQuestion({ text: draft, entrypoint: "typed" })`.
- الاقتراح: `submitQuestion({ text: suggestion.text, entrypoint: "suggestion", suggestionId })`.
- `suggestionId` لأغراض القياس والاختبار فقط؛ لا يعفي الاقتراح من التحقق ولا يمنحه مصدرًا مختلفًا عن النص نفسه.
- قفل الطلب الجاري يوضع في المتجر قبل أول `await`، مع تعطيل الأزرار ومنع الطلبات المتزامنة المكررة.
- التحقق بعد `trim`: حد أدنى 2 وأقصى 600 في الواجهة والخادم، ورسالة واضحة عند عدم الصلاحية. لا يُمسح النص قبل قبول الطلب في المتجر.
- الاقتراح «ماذا أتعلّم الآن؟» يبقى على مسار الدليل التعليمي، مع بديل نصي ثابت إذا تعذرت خدمته.

**القبول:** الضغط على «ما معنى الشهادتين؟» وكتابته يدويًا في جلسة جديدة، بنفس اللغة والموافقة والبيانات، ينتجان مدخلات دلالية متطابقة للخادم.

### R2 — معالجة الصياغة دون تغيير السؤال

إضافة وحدة مخصصة للبحث مثل `backend/app/knowledge/query_normalization.py` بدل تغيير `textcheck.normalize` المشترك مباشرة؛ لأنه يخدم أيضًا فحوص السلامة والاقتباس.

تحفظ ثلاث قيم مؤقتة: `raw_question` للعرض والفهم، `canonical_query` للبحث والكاش، و`query_variants` محدودة عند الحاجة. لا تُخزّن هذه النصوص في السجلات.

1. توحيد Unicode والمسافات والترقيم والتشكيل في نسخة البحث فقط، وفق حالات اختبار مكتوبة.
2. التعامل مع «مامعنى» عبر قاعدة بداية سؤال ضيقة ومراجعة تحولها إلى «ما معنى»، أو عبر مرادف بحث صريح. يمنع فصل كل كلمة تبدأ بـ«ما»؛ كلمة «مالك» مثال يجب ألا تتغير.
3. الحفاظ على النفي والأسماء والأرقام؛ لا تُحذف «لا» من التمثيل الدلالي المستخدم لتحديد الإجابة. يمكن بقاء سياسة stop words للبحث النصي مع اختبارات تمنع مساواة السؤال المثبت بالمنفي.
4. لا يتحول السؤال الشخصي إلى سؤال عام بسبب التطبيع. فحوص السلامة تُطبّق على النص الأصلي وأي صيغة بحث مشتقة قبل استخدامها.
5. يُحسب embedding من النص نفسه المستخدم لإنشاء مفتاح الكاش. يحتوي المفتاح على إصدار التطبيع، اللغة، واسم/إصدار نموذج التضمين. عند تغير النموذج أو الإصدار يُبطل الكاش السابق.
6. الإرسال إلى المصنف والمؤلف يظل مع السؤال الأصلي؛ يمكن تمرير الصيغة البحثية بوصفها بيانات مساعدة، ولا تُستخدم لإخفاء تفاصيل السؤال.

**القبول:** الصيغ «ما معنى الشهادتين؟»، «ما معنى الشهادتين»، «مامعنى الشهادتين»، وصيغة بتشكيل ومسافات إضافية تسترجع أدلة تغطي المعنى نفسه في مجموعة الاختبار. لا يشترط تطابق صياغة الجواب حرفيًا.

### R3 — استرجاع يمكن تفسير نتيجته

- تعيد طبقة البحث نتيجة منظمة داخليًا: المقاطع، عدد المرشحين النصيين والمتجهيين، أفضل تشابه، نوع المسار المستخدم، حالة التضمين، وسبب الفراغ. لا تُعرض التفاصيل للمستخدم.
- يُنفّذ البحث النصي والمتجهي قبل قرار عدم وجود أدلة. عند تفعيل عتبة التشابه لا ينتهي البحث قبل فحص المرشحين النصيين.
- المرشح النصي لا يصبح تلقائيًا دليلًا كافيًا. يمر بتقييم ملاءمة مضبوط بمجموعة KNW-04 وبالتحقق النهائي نفسه. لا نخفض عتبة التشابه عشوائيًا ولا نعتبر مجرد تطابق كلمة إثباتًا.
- إذا تعطلت embeddings، يُستخدم البحث النصي بوصفه وضعًا متراجعًا. إذا لم ينتج أدلة كافية، تُسجل محدودية الاسترجاع؛ لا يُعرض للمستخدم ادعاء قاطع بأن المعرفة غير موجودة.
- يسمح بمحاولة بحث إضافية واحدة بصيغ محددة مسبقًا عند ضعف التغطية، ضمن المهلة الكلية. لا تُولّد سلسلة بحث مفتوحة.
- إضافة كاسر تعادل ثابت مثل المعرّف عند تساوي ترتيب المرشحين، واختبار النسخة الباردة والدافئة للكاش.
- تُفحص تغطية المصادر واللغة ووجود embeddings للأسئلة المقترحة قبل الإطلاق. لا تُفعّل قيمة إعداد جديدة على الإنتاج لمجرد أنها حسّنت حالة واحدة.

### R4 — فصل النتيجة عن سبب الفشل

الحفاظ على الحالات الحالية وإضافة `verification_failed` لرفض الجواب بعد استنفاد المعالجة المحدودة. إضافة حقول اختيارية متوافقة مع الإصدارات السابقة: `reason_code` و`retryable`، مع تفصيل داخلي مستقل أكثر دقة.

| الحالة | السبب النموذجي | النص المقترح | الإجراء |
| --- | --- | --- | --- |
| `answered` / `cached` | جواب اجتاز الشروط أو جواب معتمد صالح | الجواب ومراجعه | حفظ، تواصل بشري عند الحاجة |
| `no_source` | لا أدلة كافية بعد بحث سليم والمحاولة المحدودة | «لم أجد في المصادر المتاحة ما يكفي للإجابة عن هذا السؤال.» | تعديل السؤال / أريد إنسانًا |
| `verification_failed` | صياغة غير مدعومة أو استشهاد غير صالح بعد المعالجة | «لم أتمكن من التحقق من إجابة موثوقة لهذا السؤال.» | تعديل السؤال / أريد إنسانًا؛ دون حلقة إعادة تلقائية |
| `unavailable` | مهلة، مزود متعطل، مدقق غير متاح، أو ميزانية | «تعذر إكمال الإجابة الآن. حاول بعد قليل، أو تواصل مع إنسان.» | إعادة المحاولة إذا كان الفشل مؤقتًا |
| خطأ اتصال | لم يصل الطلب أو لم يصل الرد | «تعذر الاتصال. تحقق من الشبكة ثم أعد المحاولة.» | إعادة المحاولة |
| HTTP 429 | حد الاستخدام | «وصلت إلى حد المحاولات. انتظر قليلًا ثم حاول.» | احترام Retry-After إن توفر |
| HTTP 422 | نص غير صالح | رسالة مرتبطة بالطول أو الحقل | تصحيح النص؛ لا يصنف كخطأ شبكة |
| `danger` / `refused` / `out_of_scope` | المسارات القائمة | الحفاظ على السلوك المختص | لا إعادة توليد لتجاوز القرار |

رموز عامة مقترحة: `retrieval_empty`، `insufficient_evidence`، `verification_rejected`، `temporarily_unavailable`، `deadline_exceeded`. التفاصيل مثل `verifier_unavailable`، `embedding_unavailable`، `provider_http_5xx`، `budget_exceeded` و`wrong_language` تحفظ داخليًا مع المرحلة، ولا تُرسل رسائل المزود الخام أو الأسرار للواجهة.

يجب ألا تكون `retryable=true` عند نفاد الميزانية أو خطأ إعداد دائم. «أريد إنسانًا» يفتح المسار القائم فقط؛ لا يُرسل نص السؤال تلقائيًا إلى طرف آخر. الاسم الحدثي `EscalationRequested` لا يُستخدم لادعاء وصول رسالة بشرية لم يرسلها المستخدم.

### R5 — معالجة الفشل بحدود واضحة

لا تُلغى محاولات `chat_json` الحالية عشوائيًا. أولًا توحّد ميزانية المحاولات والوقت على مستوى الطلب بحيث يعرف كل استدعاء الوقت المتبقي.

| الفشل | السياسة المطلوبة |
| --- | --- |
| JSON غير صالح | استخدام المحاولة الحالية ضمن ميزانية الطلب، وتسجيل السبب |
| فشل نقل مؤقت | محاولة/مزود احتياطي وفق السياسة الحالية مع احترام المهلة؛ لا سلسلة إضافية غير مضبوطة |
| لغة خاطئة أو marker غير صالح أو مصدر مفقود | إعادة صياغة واحدة موجهة بأكواد الفشل وبالمقاطع نفسها، ثم إعادة جميع الفحوص |
| `unsupported_sentence` | محاولة تصحيح واحدة لإزالة الجمل غير المدعومة، ثم تحقق كامل؛ لا إعادة فحص النص نفسه حتى يقبله المدقق صدفة |
| `insufficient` | محاولة الاسترجاع المحدودة إن لم تُستخدم، ثم صياغة وتحقق؛ وإلا `no_source` |
| `verifier_unavailable` | احتياطي المدقق ضمن الميزانية، ثم `unavailable`؛ لا عرض للجواب غير المتحقق |
| خطر/تلاعب/ميزانية نافدة/طلب غير صالح | لا إعادة تلقائية تتجاوز القرار |

الحد المقترح: جولة استرجاع أصلية وأخرى إضافية كحد أقصى، وجولة صياغة أصلية وأخرى إصلاحية كحد أقصى، مع سقف مشترك مقترح 8 نداءات خارجية يشمل embeddings والمحاولات الاحتياطية. تُخصّص حصة للتحقق قبل استهلاك الباقي، وتوقف العملية إذا لم يتبق وقت كافٍ له. لا يعني السقف وجوب استهلاكه. يعتمد التنفيذ النهائي على قياسات زمن وتكلفة ثابتة قبل الإطلاق، مع إبقاء حدود الميزانية المالية الحالية.

### R6 — نهاية واضحة للانتظار وإعادة المحاولة

- مهلة كلية مقترحة للخادم 45 ثانية تشمل جميع المراحل، ومهلة 50 ثانية للواجهة عبر `AbortController`، مع ضبط الوكيل أمام الخادم بما يسمح بوصول النتيجة المنظمة.
- تمرير الوقت المتبقي إلى نداءات AI؛ مهلة embeddings الحالية 60 ثانية لا تبقى قادرة على تجاوز مهلة الطلب الكلية.
- كل نهاية، بما فيها الإلغاء وHTTP 422 و429 و5xx وJSON غير صالح، تُخرج المتجر من `busy` وتحوّل الرسالة المعلقة إلى حالة مفهومة.
- لا تعكس مؤقتات الواجهة مراحل حقيقية؛ النص الحالي يتغير زمنيًا. يستخدم انتظار عام مثل «أبحث عن إجابة موثوقة…» ما لم تُرسل مراحل فعلية من الخادم.
- زر إعادة المحاولة يستخدم السؤال واللغة الأصليين ويحدّث رسالة المساعد الفاشلة نفسها. لا يكرر فقاعة المستخدم ولا يمسح مسودة جديدة كتبها أثناء الانتظار.
- تمنع استجابة متأخرة لطلب ملغى أو أقدم من الكتابة فوق نتيجة أحدث باستخدام معرّف المحاولة.
- احتفاظ سؤال إعادة المحاولة في الذاكرة المؤقتة للزيارة فقط؛ لا يُضاف تلقائيًا إلى تخزين دائم.
- انتهاء مهلة المتصفح لا يضمن توقف الخادم؛ لذلك يلزم أيضًا إلغاء/مهلة من جهة الخادم، ومعرّف يربط إعادة النقل بالمحاولة المنطقية.

### R7 — إجابات معتمدة للأسئلة المقترحة

تجهيز سجل معتمد للأسئلة العامة المتكررة في `content/knowledge/approved-answers.json`. يكتب المحتوى ويراجعه المسؤول المختص قبل تغيير الحالة إلى `approved`؛ لا تُعلَّم إجابة مولدة تلقائيًا على أنها معتمدة.

يتضمن كل سجل: المعرّف، اللغة، الصيغ المعروفة، الجواب، معرّفات المصادر وإصداراتها، الحالة، المراجع، وتاريخ الاعتماد. عند حذف مصدر أو تغير نسخته أو سحب اعتماده لا يستخدم الجواب حتى المراجعة.

تعديل الاستخدام المقترح: بعد فحوص السلامة والتصنيف المناسب، يبحث النظام عن تطابق صريح مع سؤال عام معتمد، ويستخدمه للمكتوب والاقتراح على السواء. عند تعطل المصنف لا يستخدم إلا تطابقًا دقيقًا لصيغة عامة معتمدة اجتازت فحوص الخطر والتلاعب؛ المطابقة الضبابية وحدها لا تكفي لمسار يتجاوز المصنف.

لا يُستخدم معرّف الاقتراح لتجاوز نص السؤال، ولا تُخزّن إجابات شخصية مشتركة بين المستخدمين. معيار Jaccard الحالي 0.75 لا يُعتبر ضمان تكافؤ المعنى؛ إضافة النفي أو وصف حالة شخصية يجب أن تمنع التطابق غير الآمن.

### R8 — مراجع واضحة دون تكرار

تجميع بطاقات العرض غير القرآنية حسب `(source_id, ref_key, lang, version)` مع معاملة الترجمات/الأعمال المختلفة كمراجع مختلفة عند الحاجة. تحتفظ طبقة التحقق بكل passage id ولا تُحذف المقاطع اللازمة لدعم الجواب. يبقى كل اقتباس قابلًا للربط بمقطعه، بينما يعرض المرجع 6940 مرة واحدة إذا كانت البطاقتان لنفس المصدر والإصدار فعلًا.

## 6. عقد API المقترح والتوافق

هذا تصميم مطلوب، وليس وصفًا لحقول موجودة حاليًا:

```json
{
  "question": "ما معنى الشهادتين؟",
  "lang": "ar",
  "consent_objectives": false,
  "client_request_id": "opaque-random-id",
  "entrypoint": "suggestion",
  "suggestion_id": "shahada_meaning"
}
```

الحقول الثلاثة الأخيرة اختيارية؛ `entrypoint` قيمة تعداد وليست نصًا حرًا. يتم التحقق من طول المعرّفات وصيغتها. لا تُسجل headers حساسة أو هوية المستخدم مع التتبع.

```json
{
  "ask_id": "server-random-id",
  "outcome": "unavailable",
  "reason_code": "temporarily_unavailable",
  "retryable": true,
  "route": "general",
  "level": "A",
  "answer": "تعذر إكمال الإجابة الآن. حاول بعد قليل.",
  "sources": [],
  "notes": [],
  "should_escalate": true,
  "handoff": {"kind": "escalation", "lang": "ar"},
  "objective_id": null,
  "lang": "ar"
}
```

- تبقى أخطاء الطلب والنقل HTTP فعلية: 422 و429 و5xx حسب الحالة؛ والنتائج المعرفية المنظمة تستخدم عقد الإجابة. لا تُحوّل جميع أخطاء النظام إلى نجاح شكلي.
- تحديث الواجهة أولًا لتتعامل بأمان مع outcome غير معروف، ثم تفعيل `verification_failed` في الخادم؛ إلى ذلك الحين يمكن عرض رسالة آمنة بالحالات المعروفة دون ادعاء عدم وجود مصادر.
- إعادة إرسال نقل المحاولة نفسها تستخدم `client_request_id` نفسه؛ إعادة المحاولة اليدوية بعد فشل نهائي تنشئ معرّفًا جديدًا وربطًا بـ`retry_of` داخليًا أو اختياريًا. منع ازدواج الآثار يتطلب تخزينًا قصير العمر مشتركًا بين العمال أو ضمانًا مكافئًا، ولا يكفي متغير في ذاكرة عامل واحد.
- إذا أضيف منع ازدواج النتائج، يقتصر على المحاولة والنطاق المناسب، مع مدة احتفاظ قصيرة معلنة، ودون تسجيل السؤال. لا يُعاد جواب مستخدم لمستخدم آخر اعتمادًا على معرّف مرسل من العميل وحده.

## 7. التشخيص والخصوصية

إضافة سجل منظم لكل محاولة يربط `ask_id` مع المراحل: `screen`، `route`، `retrieval`، `compose`، `verify` و`response`. الحقول الأساسية: `entrypoint`، `suggestion_id`، اللغة، نسخة التطبيق/الإعدادات غير السرية، المرحلة، outcome، reason، مدة المرحلة، attempt number، النموذج الفعلي، استخدام الاحتياطي، نوع cache hit، أعداد المقاطع، وأكواد التحقق.

يُضاف الربط أيضًا إلى `AiCall` و`AnswerLog` عبر migration اختيارية الحقول للصفوف القديمة. يتحقق اختبار أن السجلات لا تحتوي على نص السؤال أو الجواب أو المقاطع أو بيانات هوية. لا يُستخدم hash عادي للأسئلة كبديل مزعوم لإخفاء الهوية؛ الأسئلة الشائعة يمكن تخمينها. لمقارنة التكرار في الاختبار تستخدم معرّفات حالات مصطنعة، وفي الإنتاج تُستخدم إحصاءات مجمعة أو آلية مقيدة مستقلة عند الحاجة.

لوحة المتابعة تفصل نقص الأدلة عن أعطال المزود والمدقق والمهلات وحدود الاستخدام، وتقارن المدخل اليدوي بالاقتراحات دون استنتاج سببية من النسبة الخام؛ فالاقتراحات قد تختلف في المحتوى عن الأسئلة اليدوية. التشخيص الدقيق يعتمد على أزواج الاختبار المتطابقة.

## 8. خطة التنفيذ بالترتيب

### المرحلة 0 — تثبيت الحالة المرجعية

1. توثيق نسخة الواجهة والخادم المنشورة ومقارنتها بالأرشيف.
2. تسجيل إعدادات النماذج واللغة و`knw_min_similarity` و`knw_search_k` وحدود الوقت، دون نسخ المفاتيح.
3. إنشاء جلسات جديدة للمقارنة: اقتراح، نسخ حرفي لنص الاقتراح، وصيغ الصورة المختلفة.
4. حفظ trace تشخيصي لحالات الاختبار المصطنعة: جسم الطلب المنزوع من بيانات الهوية، نتيجة كل مرحلة، IDs المقاطع، وأسباب الرفض.
5. تثبيت نسخة بيانات المصادر والاختبار؛ مخرجات المرحلة تقرير يحدد أين يتباعد المساران. لا يُعلن سبب إنتاجي نهائي قبل ذلك.

### المرحلة 1 — إصلاح دقة الأخطاء والتتبع

فصل `verifier_unavailable` عن `no_source`، وإضافة reason codes وربط الطلب، وتحديث الواجهة والترجمات. مراجعة الاختبارات التي كانت تعتبر كل رفض تحقق «لا مصدر» وتعديل توقعاتها مع الحفاظ على منع الجواب المخالف.

**شرط الانتهاء:** حقن عطل المدقق يعطي حالة غير متاح، بينما استرجاع سليم فارغ يعطي نقص أدلة؛ يمكن معرفة المرحلة من `ask_id` دون قراءة السؤال.

### المرحلة 2 — ثبات الإرسال والانتظار

إضافة اختبار ضغط الاقتراح مقابل الكتابة، معرفات الاقتراح، مهلات الطلب، معالجة أخطاء 422/429، وإعادة المحاولة في الرسالة نفسها. اختبار الضغط السريع وتغيير اللغة والتنقل والنتيجة المتأخرة.

**شرط الانتهاء:** طلب واحد لكل فعل مقبول، وعدم بقاء `busy` بعد فشل أو مهلة، وعدم اختلاف السؤال المرسل عن المعروض.

### المرحلة 3 — الاسترجاع والتطبيع

إضافة وحدة تطبيع البحث، توحيد مدخل embedding مع المفتاح، معالجة الصيغ الملتصقة المحددة، ترتيب التعادل، وإعادة تصميم بوابة التشابه المشروطة. تقييم الدقة والاسترجاع على عينات إيجابية وسلبية قبل التفعيل.

**شرط الانتهاء:** نجاح مجموعة الصيغ دون زيادة قبول أسئلة غير مغطاة أو تغيير معنى النفي.

### المرحلة 4 — الإصلاح المحدود والإجابات المعتمدة

تطبيق ميزانية الطلب المشتركة، إعادة الصياغة المحدودة مع إعادة تحقق كاملة، وتجهيز المحتوى المعتمد للاقتراحات وإبطال سجلاته عند تغير المصدر. تجميع بطاقات المراجع في العرض.

**شرط الانتهاء:** لا تتجاوز المحاولات والوقت والميزانية، ولا يُعرض جواب اجتاز المدقق بالمصادفة بعد إعادة فحص غير محدودة، ولا يظهر سجل غير معتمد.

### المرحلة 5 — التقييم والإطلاق

تشغيل الاختبارات الآلية، ثم تقييم حي محدود التكلفة في بيئة اختبار، ثم إطلاق تدريجي مع مقارنة مؤشرات الخطأ وزمن الاستجابة. الإصلاح الذي يزيد عدد الإجابات ويُضعف موثوقيتها يفشل القبول.

### 10.2 طريقة التكرار الحي

1. اختبار الخدمات المحاكية أولًا لإثبات الواجهة والعقد؛ لا يعتمد هذا على إنفاق AI.
2. اعتماد مجموعة مرجعية من 30 سؤالًا مغطى و10 حالات سلبية/سلامة على الأقل، مع مصادر متوقعة. إضافة صيغ عربية لكل اقتراح معرفي.
3. تكرار كل اقتراح وصيغة أساسية 20 مرة في التقييم الحي، موزعة على كاش بارد ودافئ وترتيب عشوائي لمسار الإدخال. زيادة العينة عند نتائج حدودية؛ 20 محاولة ليست ضمانًا إحصائيًا مطلقًا.
4. فصل «فشل أول محاولة» عن «نجح بعد retry داخلي» وعن «احتاج إعادة يدوية» في التقرير.
5. احترام الحد الحالي 8 طلبات/دقيقة و120/يوم للعميل في الاختبارات الحية، أو استعمال بيئة اختبار مع ضبط معلن خاص بها. لا تعطيل للحماية في الإنتاج.
6. وضع سقف مالي للتقييم ضمن الميزانية المعتمدة. تجنب تفسير فشل بسبب نفاد سقف الاختبار على أنه ضعف استرجاع.
7. مراجعة جواب ومصادر، لا الاكتفاء بكون `outcome=answered`. تسجيل الإصدار ووقت الاختبار واللغة وحجم العينة.

## 11. الإطلاق والتراجع

- إضافة حقول قاعدة البيانات بصورة توافقية، ثم إصدار واجهة تدعم الحالات الجديدة، ثم تفعيل تغييرات الخادم تدريجيًا.
- فصل مفاتيح تفعيل تطبيع البحث، إصلاح الجواب، والإجابات المعتمدة لتحديد أثر كل تغيير. فصل الأخطاء الصحيح لا يعود إلى الرسائل المضللة عند التراجع.
- البدء ببيئة اختبار ثم نسبة صغيرة من الطلبات المناسبة ثم التوسع، بشرط توفر عينة كافية للمقارنة. يمكن استخدام 5% ثم25% ثم100% كنسب تشغيل مقترحة.
- التراجع الفوري عند عرض جواب غير متحقق أو مرجع مختلق. التراجع عن الجزء المتسبب عند انخفاض نجاح المجموعة المرجعية بأكثر من نقطتين مئويتين، أو زيادة P95 بأكثر من20% مقارنة بالخط الأساسي، بعد التحقق من حجم العينة وحالة المزود.
- عند التراجع لا تحذف السجلات التشخيصية أو migration بشكل مدمر؛ عطّل الميزة الجديدة واحتفظ بإمكان التحقيق.

## 12. تعريف الاكتمال

لا تُغلق المشكلة لمجرد أن السؤال نجح مرة واحدة. تكتمل عندما:

- تثبت اختبارات الواجهة أن الاقتراح والنص يتبعان عقدًا واحدًا.
- تُحسم حالة الصورة ومثيلاتها باختبارات صيغ ومراحل موثقة، مع بيان السبب الذي أمكن إثباته.
- لا يُعرض عطل المدقق على أنه نقص مصادر، ولا يبقى انتظار بلا نهاية.
- تحقق مجموعة الإصدار أهداف الجودة والثبات والسلامة والزمن أو يُوثق قرار منتج صريح لتعديل هدف قبل الإطلاق.
- تظل كل إجابة مدعومة بمصادر معتمدة وتظل الحالات الخطرة والشخصية على مساراتها.
- تُراجع إجابات الاقتراحات المعتمدة وتُختبر صلاحية مصادرها، دون قبول آلي للاعتماد.
- تُوثق نتيجة الاختبارات، إعدادات التشغيل غير السرية، تكلفة التقييم، وخطة التراجع في تقرير التنفيذ.

## 14. تفاصيل التنفيذ الملزمة للمطور المستلم

هذا القسم يحسم القرارات التي قد تؤدي إلى إصلاح جزئي أو غير صحيح. أسماء الأنواع والدوال المقترحة قابلة للتكييف مع بنية المشروع الحالية، أما السلوك والاختبارات فمطلوبان.

### 14.1 ترتيب قرار النتيجة وتحديد مسؤولية كل طبقة

تُحوّل نتيجة التحقق إلى نوع منظم، مثل:

```text
VerificationResult:
  status: passed | rejected | unavailable
  codes: list[known_code]

RetrievalResult:
  passages: list[passage]
  status: complete | degraded | unavailable
  reason: known_code | null
  vector_count: integer
  text_count: integer
  max_similarity: number | null

RequestContext:
  ask_id
  deadline_monotonic
  external_calls_used
  retrieval_rounds_used
  compose_rounds_used
```

قواعد التحويل، حسب الأولوية:

1. الخطر والتلاعب وخارج النطاق لها مساراتها، ولا تتحول إلى بحث متكرر عن جواب مقبول.
2. فشل اتصال قاعدة البيانات أو خطأ SQL لا يعني عدم وجود مصادر. يعالج كعطل، مع rollback عند الحاجة. لا يصح أن تلتقط `_text_hits` أي استثناء وتجعله قائمة فارغة دون الاحتفاظ بسبب الفشل.
3. إذا نجح مسار استرجاع بديل وأنتج أدلة كافية، يمكن إكمال الإجابة رغم تراجع المسار الآخر، ثم التحقق الكامل.
4. إذا تعطلت embeddings ولم يقدم البحث النصي دليلًا كافيًا، تكون النتيجة `unavailable` مع سبب داخلي `retrieval_degraded_no_evidence`، لا `no_source` قطعيًا. أما فشل استرجاع كامل وسليم في إيجاد أدلة فيعطي `no_source`.
5. `VerificationResult.status=unavailable` يعطي `unavailable` دائمًا بعد الاحتياطي المحدود. لا يعامل كرفض محتوى ولا يؤدي إلى إعادة كتابة الجواب بلا داعٍ.
6. إذا كان سبب الرفض الوحيد `insufficient`، يسمح بجولة الاسترجاع الإضافية. بعد استنفادها وعدم كفاية الأدلة تعاد `no_source`. إذا اجتمع معه مرجع غير مسترجع أو مخالفة أخرى، تُعالج المخالفات أولًا ولا تُخفى تحت «نقص مصدر».
7. أي مخالفة محتوى غير محلولة بعد جولة الإصلاح تعطي `verification_failed`، ولا تحمل الردودة أي نص مولد مرفوض أو بطاقات توحي بأنه موثق.
8. لا يُرجع `answered` إلا بعد اجتياز التحقق، ووجود كل المصادر المطلوبة عند بناء البطاقات النهائية. إذا اختفى مصدر بين الاسترجاع وبناء الرد، فلا يعرض جواب ناقص الإسناد.
9. الحالة `cached` تخص جوابًا معتمدًا حاليًا، مع فحص صلاحية المراجع والإصدارات واللغة والتطابق؛ لا تعني إعادة جواب مولد سابق لمجرد نجاحه مرة.

يُمنع استخدام `except Exception: return no_source` كمعالجة عامة. الأخطاء غير المتوقعة تُسجل برمز آمن وترجع حالة خطأ تقنية مناسبة، مع إنهاء حالة الانتظار في الواجهة.

### 14.2 خوارزمية الطلب بعد الإصلاح

```text
validate trimmed question and language
create request context and total deadline
run safety screens on the original input
detect learning-guide path and finish it with a bounded fallback
build search-only canonical query and safe bounded variants
route question, or use only an exact approved general FAQ fallback if routing is unavailable
apply danger / manipulation / out-of-scope route decisions
match a valid approved general answer for eligible questions
otherwise retrieve with structured diagnostics
if retrieval is insufficient, expand once when allowed
compose using approved retrieved passages only
run deterministic checks, then semantic support verification
if repairable rejection, repair once and re-run every check
build source cards and confirm completeness
persist required effects without duplication
return the typed result
```

التوسيع ليس جولة مستقلة تُضاف مرة قبل التأليف ومرة بعد `insufficient`؛ عداد `retrieval_rounds_used` مشترك، وبحد أقصى جولتين في الطلب كله. وبالمثل، جولة الإصلاح أو التأليف بعد توسيع متأخر تستهلك الجولة الثانية من حد التأليف؛ لا ينشأ استثناء يعيد ضبط العداد.

تمرير `RequestContext` إلى النداءات بدل عدادات مستقلة داخل كل دالة. كل نداء خارجي، بما فيه fallback وJSON retry، يستهلك من السقف نفسه. قبل النِّداء تُفحص الميزانية المالية والوقت المتبقي وحد المحاولات؛ نفاد أي منها ينهي الطلب بحالة صحيحة. استخدام موعد monotonic يمنع تأثر المهلة بتغير ساعة النظام.

### 14.3 دورة حالة الواجهة والإلغاء

لكل سؤال: `turnId` ثابت، ولكل تشغيل فعلي `attemptId` جديد. الحالات المطلوبة:

```text
idle → pending → done
               → error
               → cancelled
error → pending (same turnId, new attemptId)
```

- التحقق من الطول والحالة يتم قبل إضافة الفقاعات. تحفظ لقطة `{question, lang, consent_objectives, entrypoint, suggestion_id}` في الذاكرة لإعادة المحاولة؛ لا تؤخذ اللغة من الواجهة الحالية عند retry.
- `finally` لا يضبط `busy=false` لطلب أحدث: يحرر القفل فقط إذا كان `attemptId` لا يزال هو المحاولة النشطة.
- رد attempt قديم يُهمل قبل تحديث الرسالة. الإلغاء يعالج كإلغاء واضح، والمهلة تعالج كمهلة؛ لا يظلان pending.
- مهلة الـ50 ثانية تخص المحاولة كاملة، بما فيها تجديد جلسة المصادقة وإعادة الطلب مرة عند 401. لا تُنشأ مهلة جديدة كاملة لكل refresh. يجب ألا تتسبب إضافة abort في إلغاء تجديد مشترك تحتاجه طلبات أخرى.
- الدليل التعليمي له نهاية واضحة أيضًا: فشل أو مهلة `requestGuide` ينتقلان إلى `fixedMessage`؛ لا يظل الرد `learning_guide` مع مؤشر انتظار دائم.
- يُحتفظ بوظائف Enter وShift+Enter وعدم الإرسال أثناء IME composition. إضافة اختبارات لذلك عند تعديل مكون الإدخال.
- تحليل جسم HTTP يحاول JSON بأمان؛ إذا عاد HTML في خطأ 502 يحتفظ الكود بالحالة 502 ولا يستبدلها بخطأ parse مبهم. استجابة 200 بعقد غير صالح تعرض `invalid_response` آمنًا ولا تمرر undefined إلى مكون العرض.

### 14.4 المعاملات والعمليات اللاحقة للإجابة

المسار الحالي ينفذ بعد التحقق بعض العمليات مثل `tasks.tag_question` عند الموافقة، ونشر الأحداث وكتابة السجل ثم `commit`. يجب اختبارها؛ فنجاح التوليد لا يعني أن الرد وصل إذا فشل عمل لاحق.

- تصنيف الهدف التعليمي عمل اختياري: إذا فشل أو نفد وقته بعد جاهزية جواب متحقق، يرجع الجواب مع `objective_id=null`، مع تسجيل تعطل التصنيف. لا يفشل السؤال كله بسبب هذا العمل.
- فشل كتابة سجل تشخيصي وحده لا يحول جوابًا متحققًا إلى «لا مصدر». يُعزل عن معاملة الآثار المطلوبة، بآلية معتمدة في المشروع، مع رصد الفشل دون نص المستخدم.
- الأحداث المطلوبة التي يلزم ضمانها تُكتب بمعاملة/outbox مناسب إن كان متوفرًا، أو آلية متينة مكافئة. لا ينشئ Claude اعتمادًا جديدًا على broker لمجرد هذه الوثيقة إذا تكفي بنية المشروع.
- فشل حفظ أثر مطلوب يرجع خطأً تقنيًا واضحًا حسب العقد، ولا يدعي نجاح إرسال بشري. إعادة الطلب لا تكرر الحدث أو احتساب الهدف.
- لا تُعاد استخدام AsyncSession بعد خطأ SQL دون rollback، ولا تُشارك الجلسة نفسها بين مهام استرجاع متزامنة. يمكن تنفيذ الاستعلامات بالتتابع أو استخدام جلسات مستقلة عند الحاجة.

### 14.5 الإعدادات والترحيل

تُعرّف الإعدادات التالية في آلية Settings الحالية وتُوثق في مثال البيئة دون أسرار:

| إعداد مقترح | القيمة الابتدائية | الملاحظة |
| --- | --- | --- |
| `ASK_DEADLINE_SECONDS` | 45 | تشمل pipeline والأعمال المطلوبة قبل الرد |
| `ASK_MAX_EXTERNAL_CALLS` | 8 | جميع مراحل AI وembeddings، لا لكل مرحلة |
| `ASK_MAX_RETRIEVAL_ROUNDS` | 2 | الأصلية + توسعة واحدة |
| `ASK_MAX_COMPOSE_ROUNDS` | 2 | الأصلية + إصلاح/تأليف إضافي واحد |
| مهلة واجهة السؤال | 50000 ms | أكبر من مهلة الخادم؛ مرجع واحد في كود الواجهة |
| `ASK_QUERY_NORMALIZATION_ENABLED` | false قبل التقييم | يفعّل بعد اختبار الصيغ والكاش |
| `ASK_REPAIR_ENABLED` | false قبل التقييم | يفعّل بعد اختبارات السلامة والوقت |
| `ASK_APPROVED_FAQ_ENABLED` | false حتى اعتماد المحتوى | لا يفعّل ملفًا فارغًا أو غير معتمد |

هذه أسماء وقيم تنفيذية مقترحة تُطابق مع أسلوب المشروع؛ لا يُدعى أنها موجودة حاليًا. فصل الأخطاء وإتمام حالة الانتظار لا يتوقفان على مفاتيح الميزات التجريبية.

الترحيل يضيف أعمدة قابلة لـNULL للبيانات السابقة، وفهرسًا مناسبًا لـ`ask_id`، دون نسخ نصوص أسئلة. يختبر upgrade على قاعدة اختبار بها صفوف قديمة، ويختبر تشغيل الإصدار السابق مع الأعمدة المضافة. لا يستخدم downgrade يحذف سجلات الإنتاج كخطة تراجع. تُراجع مهلة reverse proxy من ملف النشر الحقيقي إن وجد؛ لا يُخترع اسم ملف إعداد غير موجود.

### 14.6 عدم تحويل تحسين إضافي إلى سبب لإخفاء العطل

الإجابات المعتمدة تقلل التفاوت للأسئلة الشائعة، لكنها لا تعوض اختبار مسار البحث والتوليد. تشغّل مجموعة القبول مرتين: مع مسار FAQ معطّل لتقييم الإصلاح العام، ومعه مفعّل لاختبار الاعتماد والإبطال. إذا غاب اعتماد المحتوى، ينفذ الكود واختباراته ببيانات fixtures مصطنعة، ويذكر بوضوح أن إطلاق FAQ ما زال معلقًا؛ لا يعتمد المحتوى نيابة عن المراجع.

تجميع بطاقات المصادر تحسين عرض تابع؛ يُفصل في التغييرات بحيث لا يعوق إصلاح أخطاء الإرسال والتشخيص. لا يُنفذ استبدال شامل للتصميم أو المعمارية ضمن هذه المهمة.

### 14.7 اختبارات تكميلية لازمة

تضاف إلى T01–T22:

| ID | الحالة | النتيجة المطلوبة |
| --- | --- | --- |
| T23 | SQL error مقابل بحث سليم بلا نتائج | عطل تقني للأول وno_source للثاني؛ صلاحية الجلسة بعد rollback |
| T24 | رفض المدقق مع embeddings متعطلة أو أسباب متعددة | تطبيق أولوية الأسباب وعدم عرض نص مرفوض |
| T25 | فشل tag_question مع الموافقة بعد نجاح التحقق | بقاء الجواب الصحيح، objective_id=null، دون حدث هدف وهمي |
| T26 | فشل سجل تشخيصي أو commit لأثر مطلوب | سلوك واضح حسب نوع العملية، دون no_source مضلل أو أثر مكرر |
| T27 | انتهاء المهلة أثناء refresh المصادقة أو الدليل التعليمي | انتهاء المحاولة في الوقت الكلي أو بديل الدليل؛ دون انتظار دائم |
| T28 | استنفاد جولات البحث/التأليف والمحاولات داخل fallback | لا تجاوز لسقف مشترك ولا إعادة ضبط للعدادات |
| T29 | حذف/تغيير مصدر قبل تكوين البطاقات النهائية | عدم عرض answered ناقص الإسناد |
| T30 | FAQ معطل ومفعّل مع نفس مجموعة الأسئلة | قياس إصلاح المسار العام مستقلًا عن تغطية FAQ |
| T31 | استجابة 200 غير مطابقة للعقد و502 بجسم HTML | حالة خطأ مفهومة دون تعطل مكونات العرض |
| T32 | ترحيل على بيانات قديمة وتراجع عن مفاتيح التفعيل | استمرار القراءة وعدم حذف بيانات أو تعطيل النسخة السابقة |

### 14.8 ملف إثبات التنفيذ المطلوب من Claude

بعد التنفيذ يُنشأ `docs/engineering/implementation/KNW-01-chatbot-reliability-report.md` وفيه:

1. نسخة الكود والبيانات التي جرى عليها الاختبار.
2. السبب الذي أعيد إنتاجه، وأي فرضيات لم تثبت، مع ربط السبب بالاختبار والإصلاح.
3. جدول R1–R8 وT01–T32: منفذ، ناجح، فاشل، أو لم يُشغّل، مع سبب ودليل لكل حالة غير ناجحة.
4. أوامر التشغيل الفعلية ونتائجها، ومقاييس أول محاولة والتكرار والزمن والتكلفة قبل/بعد.
5. الفرق بين تحقق محلي بخدمات محاكية وتحقق حي بالخدمات وقاعدة المصادر الفعلية.
6. خطوات النشر والتراجع والمحتوى أو الاعتمادات المتبقية. لا تُستخدم عبارة «تم حل المشكلة بالكامل» إذا بقي اختبار قبول مطلوب غير مشغّل أو فاشل.
