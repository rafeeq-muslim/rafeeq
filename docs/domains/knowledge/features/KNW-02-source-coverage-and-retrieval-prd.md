## 1. الإجابة المباشرة: هل توجد مشكلة فعلًا؟

**نعم، توجد فجوة مؤكدة في إعدادات النسخة المرفقة بالنسبة إلى توقع استخدام «الإسلام سؤال وجواب»: المصدر `islamqa` موجود في الاستيراد، لكنه مستبعد من قائمة مصادر الإجابة الافتراضية.** البحث النصي والمتجهي يرشحان المصادر بهذه القائمة، ومهمة embeddings الدورية تستخدم القائمة نفسها. إذا كانت بيئة التشغيل تستخدم القيمة الافتراضية، فلن يدخل الإسلام سؤال وجواب في إجابات الشات حتى لو كانت بياناته مستوردة أو كان لدى المطور اتصال MCP به.

القيمة الحالية في `backend/app/core/config.py:42`:

```text
quranenc,hadeethenc,islamhouse_enc,binbaz
```

المصدر المقصود بالإسلام سؤال وجواب هو `islamqa` / `islamqa.info`؛ أما `islamhouse_enc` فهو مصدر آخر ولا يغني عنه.

**لا يوجد دليل كافٍ على أن كثرة ابن باز وحدها خلل في الترتيب.** قد تكون مواده الأنسب للأسئلة العربية المطروحة. الخلل هو استبعاد مصدر مقصود دون وضوح، أو عدم جاهزية بياناته، أو إسقاط أدلته المناسبة أثناء الاسترجاع. ليس المطلوب توزيع الإجابات 50/50 ولا إظهار المصدرين في كل جواب.

لم تُقرأ قيمة البيئة الحية `KNW_ANSWER_SOURCES`، ولم تُفحص قاعدة الإنتاج أو إعداد MCP الذي أشار إليه المستخدم. لذلك النتيجة المؤكدة تخص الإعداد الافتراضي ومسار الكود، لا إثبات سبب كل جواب سابق في الإنتاج.

## 2. الفرق بين MCP ومصادر الشات الحالية

المسار الفعلي الذي تمت مراجعته:

```text
ملفات مصدر خارج المستودع
  → normalizer لكل مصدر
  → ملفات corpus بصيغة JSONL
  → app.knowledge.load
  → knw_sources + knw_passages
  → embeddings + فهرس نصي
  → search(question, lang) مع فلتر KNW_ANSWER_SOURCES
  → مقاطع محدودة → مؤلف الجواب → مدقق → مصادر الجواب
```

لم يظهر استدعاء عميل MCP في مسار `ask.py → search.py → agents.py`. البحث هنا على PostgreSQL، وليس استدعاءً مباشرًا لأدوات الموقعين. وملف `docs/engineering/ai-tools.md` يصف بعض أدوات MCP كأدوات تطوير/استيراد، كما يصف مجلد tools المقترح بوصفه تصميمًا؛ وجوده في الوثائق لا يثبت تنفيذه.

قد يكون اتصال المستخدم قائمًا في إعدادات Claude خارج الأرشيف أو في خدمة منفصلة. المطلوب من المطور تحديد موضعه الفعلي ونوعه دون الافتراض أنه غير موجود:

| مكان الربط | ما يثبته | ما لا يثبته |
| --- | --- | --- |
| MCP متاح داخل Claude | يستطيع Claude استدعاء الأدوات | أن تطبيق رفيق يستدعيها |
| MCP مستخدم في تجهيز البيانات | توجد وسيلة للحصول على محتوى | أنه حُمّل إلى قاعدة بيانات التطبيق الحالية |
| بيانات موجودة في `knw_passages` | المصدر مستورد | أنه مفعّل أو له embeddings أو يصل إلى المؤلف |
| مصدر ضمن قائمة الإجابة | مؤهل للبحث من ناحية الإعداد | أن مقاطعه مناسبة أو مستشهد بها |
| مقاطع وصلت للمؤلف | المصدر استُرجع | أن الجواب اعتمد عليها فعلًا واجتاز التحقق |

**قرار النطاق:** إصلاح مسار الفهرس المحلي الموجود أولًا. لا تُضاف مكالمات MCP حية إلى كل سؤال لمجرد تنويع الأسماء. إذا وجد المطور مسار MCP فعليًا في النسخة الأحدث، يقيسه ويوثّق الاختلاف قبل تعديل الخطة؛ ويبقي عقد المصدر والتحقق والتتبع موحدًا.

## 4. شجرة التشخيص المطلوبة قبل التغيير

1. اقرأ **القيمة الفعلية** لـ`get_settings().knw_answer_sources` من العملية/الحاوية التي تخدم `/api/ask`، لا من ملف محلي غير مستخدم. اعرض هذا الحقل فقط؛ لا تطبع كل Settings أو ملف الأسرار.
2. إذا غاب `islamqa`، فهذا سبب كافٍ لعدم استرجاعه من هذا المسار. سجّل `disabled_by_answer_config` وانتقل لفحص جاهزية البيانات قبل التفعيل.
3. إذا كان مفعّلًا، افحص وجود Source وصفوف اللغة المطلوبة ثم تغطية embeddings والفهرس النصي.
4. إذا كانت الصفوف موجودة بلا متجهات، اختبر البحث النصي وحده والمتجهي وحده. نقص المتجهات لا يعني أن البحث النصي مستحيل.
5. إذا كانت البيانات جاهزة، افحص عدد مقاطع islamqa في المرشحين الأوليين، ثم بعد الدمج، ثم آخر k، ثم المراجع التي اختارها المؤلف والمدقق.
6. إذا لم تسترجع المقاطع المعروفة حتى عند قصر التشخيص على islamqa، فالمشكلة في الاستيراد/اللغة/البحث أو السؤال المرجعي، وليس في مقارنة المصدرين.
7. إذا استرجعت جيدًا منفردة وتختفي في الدمج، قيّم ازدحام المقاطع والترتيب. لا تُفرض نسب مسبقة قبل هذه النتيجة.
8. إذا وصلت للمؤلف ولم يستشهد بها، راجع ملاءمتها فعلًا واقتطاع محتواها في `agents.passage_block` وجودة الإسناد؛ ليس كل مصدر مسترجع واجب الظهور في الرد.

## 5. أدوات تحقق قابلة للتنفيذ

هذه أوامر تشخيص مقترحة للمطور من بيئة التطبيق، لم تُشغّل ضمن إعداد PRD. لا تطبع بيانات اعتماد أو أسئلة مستخدمين.

### 5.1 الإعداد الفعلي

من مجلد backend داخل بيئة التشغيل الصحيحة:

```bash
python -c "from app.core.config import get_settings; s=get_settings(); print({'answer_sources':s.knw_answer_sources, 'search_k':s.knw_search_k, 'min_similarity':s.knw_min_similarity, 'embed_job_limit':s.knw_embed_job_limit})"
```

`get_settings` مخزنة بـlru_cache. بعد تغيير البيئة يلزم إعادة إنشاء/تشغيل عمليات backend والـscheduler التي تقرأها حسب آلية النشر، ثم قراءة القيمة مجددًا من كل نسخة فعالة. تعديل ملف البيئة مع إبقاء الحاوية القديمة لا يضمن تطبيق المتغير الجديد.

### 5.2 مخزون المصادر — SQL للقراءة فقط

```sql
SELECT s.id, s.mode, p.lang,
       COUNT(p.id) AS passages,
       COUNT(p.id) FILTER (WHERE p.embedding IS NOT NULL) AS embedded,
       COUNT(p.id) FILTER (WHERE p.tsv IS NOT NULL AND length(p.tsv) > 0) AS searchable_text,
       ROUND(100.0 * COUNT(p.id) FILTER (WHERE p.embedding IS NOT NULL)
             / NULLIF(COUNT(p.id), 0), 2) AS embedding_pct
FROM knw_sources s
LEFT JOIN knw_passages p ON p.source_id = s.id
GROUP BY s.id, s.mode, p.lang
ORDER BY s.id, p.lang;

SELECT source_id, lang, version, COUNT(*) AS passages
FROM knw_passages
WHERE source_id IN ('binbaz', 'islamqa')
GROUP BY source_id, lang, version
ORDER BY source_id, lang, version;
```

القيم المرجعية الموجودة في وثائق البحث القديمة ليست أعداد الإنتاج الحالية. عدم وجود row لـislamqa يختلف عن وجوده بصفر مقطع؛ يسجل تقرير التشخيص الحالتين بوضوح. `embedding IS NOT NULL` يثبت وجود متجه فقط، ولا يثبت أنه محسوب بالنموذج الحالي؛ تُراجع نسخة تشغيل تجهيز المتجهات وسجلها أيضًا.

### 5.3 اختبار مصدر واحد ثم المقارنة

إضافة أداة تشخيص داخلية مقترحة `backend/app/knowledge/source_diagnostics.py`، تستخدم دوال البحث نفسها، وتقبل سؤال fixture مصطنعًا واللغة والمصادر المقيدة. لا تضيف endpoint عامًا يسمح للمستخدم بتجاوز السياسة.

المخرجات المطلوبة، دون نصوص خاصة: `source_id`, `ref_key`, `passage_id`, `retrieval_channel`, `rank`, `similarity`, `selected_for_context`, `cited_in_answer`, `exclusion_reason`. درجات cosine منفصلة عن RRF؛ لا تُقارن قيمتان مختلفتان بوصفهما درجة واحدة.

تشغيل الحالات ذات الأدلة المعروفة تحت: `[islamqa]`، `[binbaz]`، ثم القائمة الموحدة. إذا تطلب التشخيص تجاوز قائمة الإنتاج المستبعدة، يتم ذلك في بيئة اختبار وفهرس اختبار واضحين، دون فتح تجاوز في طلبات المستخدمين.

## 6. المتطلبات التقنية للإصلاح

### SC1 — سياسة مصدر واحدة ومتسقة

إضافة محلل مركزي للقائمة في وحدة مثل `backend/app/knowledge/source_policy.py`، يعيد أسماء المصدر بعد trim، حذف الفراغات والتكرارات، والتحقق من الأسماء المعروفة. تستخدمه search والـjobs وأداة التشخيص بدل محللين مختلفين؛ `jobs.py` الحالي لا يطبق strip مثل البحث.

فصل المفاهيم صراحةً:

- `configured_for_answers`: مطلوب استخدامه وفق إعداد المنتج.
- `index_mode`: هل يسمح السجل باستخدام المحتوى في الفهرس، أم هو رابط فقط؟
- `available_languages`: مشتقة من البيانات/سجل المصدر، ولا تُختلق ترجمة.
- `data_ready`: عدد المقاطع وحالة الفهرس والمتجهات.
- `effective_for_request`: مؤهل لهذا الطلب، مع سبب الاستبعاد إن لم يكن.

التفعيل المطلوب لمطابقة توقع المنتج يشمل القائمة:

```text
KNW_ANSWER_SOURCES=quranenc,hadeethenc,islamhouse_enc,binbaz,islamqa
```

يُطبّق بعد التحقق من بيانات المصدر وسياسة المشروع المقصودة، دون افتراض أن تغيير default يكفي لتجاوز override في بيئة النشر. يوثق المطور هذا كإزالة تعارض الإعداد مع المصادر المقصودة، ويحافظ على حالة المصدر التاريخية المسجلة.

تُستخدم قائمة الأهلية المركزية في البحث النصي والمتجهي والإجابات المعتمدة المحفوظة عند إعادة تقديمها. تغيير `mode=link` أو تعطيل المصدر يجب أن يمنع استخدام محتواه في إجابات جديدة حتى إذا بقيت المقاطع داخل DB. الاستيراد لا يمنح بمفرده إذنًا تلقائيًا للعرض.

دلالة الفلتر: `sources=None` تعني المصادر المؤهلة الافتراضية، و`sources=[]` تعني لا مصادر فتعود نتيجة فارغة؛ القائمة الصريحة تُتقاطع مع السياسة في مسار الإنتاج. يمنع fallback الذي يحوّل استبعاد كل المصادر إلى البحث في جميعها.

### SC2 — استيراد لا ينجح ظاهريًا ببيانات مفقودة

إذا لم توجد البيانات، تُجهز عبر مسار الاستيراد الموجود. لا يلزم تنزيل جديد إذا توفر corpus صالح. الترتيب:

1. فحص ملف islamqa JSONL، عدد الصفوف، source_id، اللغة، النص، رابط الأصل، version، والتكرارات.
2. رفض استيراد ملف فارغ أو تالف بوصفه تحديثًا طبيعيًا. `load_source` يحذف الصفوف القديمة التي لم تعد في الملف، لذلك لا يُستخدم ملف ناقص لتحويل عطل تنزيل إلى حذف كامل للمصدر.
3. عند تحديد `python -m app.knowledge.load islamqa` يجب أن يفشل الأمر بوضوح إذا كان الملف المطلوب غير موجود. المسار الحالي يمشي على الملفات المتاحة وقد ينتهي دون تحميل المصدر المحدد؛ يُضاف فحص ذلك.
4. سجل manifest بعدد المواد والإصدار وحالة اكتمال التصدير. انخفاض كبير غير متوقع في العدد يُوقف الاستبدال للمراجعة التقنية؛ حذف كامل مقصود يحتاج مسار إدارة مستقل.
5. تحميل النسخة المعتمدة في معاملة كما يدعم loader الحالي، ثم مقارنة العدد واللغات والإصدارات ومصادر الروابط. لا مسح شامل للقاعدة.

إذا كان MCP هو وسيلة جمع البيانات الفعلية في النسخة الأحدث، يتحول ناتجه إلى عقد Passage نفسه مع source_id الأصلي، origin_url، version وquote/context. لا يستخدم اسم خادم MCP بديلًا عن المصدر الحقيقي، ولا يُسجل نص مولد كأنه نص المصدر.

### SC3 — تجهيز embeddings للمصدر الثاني

من backend وفي بيئة مناسبة:

```bash
python -m app.knowledge.embed --source islamqa --lang ar --estimate
python -m app.knowledge.embed --source islamqa --lang ar --limit 2000 --batch 64
```

الأول تقدير فقط؛ الثاني يُجري نداءات مدفوعة ويلتزم بسقف تشغيل المشروع. تقدير التكلفة الموجود في الكود ليس سعرًا حيًا مضمونًا. تبدأ دفعة اختبار، ثم تستكمل الدفعات عند الحاجة ضمن الميزانية دون إلغاء الحارس المالي أو إعادة embedding للمقاطع السليمة بلا سبب.

- تسجل نسبة التغطية لكل مصدر ولغة، وعدد المتبقي، وآخر نجاح وسبب التوقف.
- لا يعلن المصدر جاهزًا للبحث المتجهي لأن بعض الدفعات انتهت؛ الحالات المرجعية كلها تحتاج متجهات سليمة، وخطة الإطلاق الكاملة تستهدف إكمال المقاطع المفعلة أو إعلان الوضع المتراجع بوضوح.
- توحيد اختيار مصادر الـscheduler مع السياسة المركزية، وتوزيع الدفعات بين المصادر ذات العمل المتبقي إذا أثبت القياس تأخر مصدر بسبب الترتيب الأبجدي. لا تُفرض إعادة هيكلة للجدولة قبل إثبات الحاجة.
- تغيير نموذج التضمين يستدعي إصدار فهرس متوافق وإعادة تجهيز صحيحة؛ مساواة الأبعاد وحدها ليست دليل توافق المتجهات.
- لا تتسبب دفعات الاستيراد في استهلاك ميزانية الإجابة كلها دون مراقبة؛ يُجدول العمل ويُراقب السقف الموجود.

### SC4 — اختيار الأدلة حسب الجودة دون إقصاء صامت

الإصلاح الأساسي هو الإعداد والجاهزية. بعده يُقاس الاسترجاع قبل أي تعديل للترتيب.

في حال ثبوت ازدحام المصدر/المرجع الواحد:

1. تستمر مقارنة المقاطع وفق الملاءمة واللغة، مع ترتيب تعادل ثابت بالمعرّف.
2. تضبط كمية المقاطع المتكررة من المرجع نفسه عند اختيار السياق، مع الاحتفاظ بمقاطع إضافية لازمة لتغطية الجواب. بطاقة مصدر واحدة لا تعني حذف أدلة لازمة.
3. يمكن تجربة جمع عدد محدود من المرشحين لكل مصدر ثم دمجهم وترتيبهم عالميًا. حجز مرشح للمقارنة لا يعني فرضه ضمن سياق الجواب أو الاستشهاد به.
4. لا تستخدم RRF المحلي لكل مصدر كدرجة عالمية بلا معايرة؛ المرتبة الأولى في مصدر ضعيف لا تساوي دليلًا أقوى من مصدر آخر. يُختبر الدمج على مجموعة ملاءمة معلّمة، وتبقى الأدلة الضعيفة خارج السياق.
5. يظل حجم السياق والمهلة والميزانية من PRD الأول مطبقًا. لا تُجرى نداءات نموذج غير محدودة للحصول على «تنوع».
6. لا يطلب prompt من المؤلف ذكر اسلام سؤال وجواب أو ابن باز إذا لم يستند الجواب فعليًا إلى مقاطعه. يتحقق المدقق من كل مرجع كما هو.

**عدم وجود هدف حصة ثابتة شرط منتج:** جواب موثّق من ابن باز وحده يظل صحيحًا إذا كان الأنسب، وجواب موثّق من islamqa وحده كذلك. نجاح الإصلاح يُقاس بوصول الأدلة المتوقعة في حالات معلومة، وليس بتوازن أسماء البطاقات.

### SC5 — المصدر الأصلي في العرض

`source_id` واسم المصدر والرابط في الجواب تأتي من المقطع/سجل المصدر، لا من تخمين النموذج. `frontend/src/app/ask/parts.tsx` يحتوي اختصارات لمصادر منها binbaz، ولا يحتوي islamqa في جدول الاختصارات المعروض؛ يوجد fallback إلى source_name، لذلك غياب الاختصار وحده ليس سبب اختفاء المصدر من البحث. يضاف اختصار `islamqa.info` لتحسين العرض مع اختبار الاسم والرابط.

يُجمع عرض البطاقات على مستوى المرجع وفق PRD الأول، وتبقى المقاطع في التحقق. إذا نقل islamqa كلامًا لابن باز، فلا يُستنتج أن الرابط كان من موقع ابن باز: يميز العرض بين الموقع المسترجع والمؤلف المذكور داخل المحتوى إن توفرت هذه البيانات.

### SC6 — رصد موضع اختفاء المصدر

يرتبط التتبع بمعرّف الطلب الذي يحدده PRD الأول، مع عدادات لكل مصدر في المراحل:

```text
configured → eligible → candidates → context → cited → verified/displayed
```

أسباب الاستبعاد المقترحة: `disabled_by_answer_config`، `mode_link`، `missing_source`، `no_passages_for_lang`، `embedding_pending`، `no_relevant_hits`، `below_threshold`، `context_limit`، `not_cited`، `verification_rejected`.

لا يسجل «لم يُستشهد به» على أنه «لم يُبحث فيه». لا تنشر بيانات إدارة المصادر أو تكوين MCP في endpoint عام. تقرير الصحة داخلي، خالٍ من المفاتيح والأسئلة الخاصة، ويبين المصادر المقصودة غير الجاهزة. تظل الخدمة تعمل بالمصادر السليمة بدل تعطيلها كلها بسبب مصدر واحد.

## 8. التنفيذ والإطلاق

1. **إثبات خط الأساس:** استخراج القيمة الفعلية الآمنة ومخزون المصدرين، وتوثيق مكان MCP إن كان متاحًا. لا إعادة تنزيل أو استيراد قبل معرفة الناقص.
2. **اختبار يعيد إنتاج المشكلة:** fixture فيها المصدران مع دليل موجود فقط في islamqa؛ إثبات أن إعداد النسخة الافتراضي يستبعده. ليس مطلوبًا مزود حي لهذا الاختبار.
3. **سياسة موحدة وإصلاح الإعداد:** تنفيذ SC1 واختبار المسارين والـscheduler. المحافظة على المصادر السابقة وإضافة المقصود بدل استبدالها.
4. **سد فجوات البيانات فقط:** استيراد أو embeddings للمصدر/اللغة الناقصة مع فحص عدد الصفوف والتكلفة قبل وبعد.
5. **اختبار الترتيب كما هو:** إذا نجحت الحالات المرجعية بعد الإعداد والجاهزية، لا تغيير شامل للترتيب. إذا فشلت، تطبيق تجربة SC4 ومقارنتها بالخط الأساسي.
6. **عرض وتتبع:** بطاقات صحيحة وتقرير مراحل يشرح أي استبعاد.
7. **تقييم قبل النشر:** اختبارات محلية، ثم عينة حيّة محدودة؛ فصل نقص المعرفة وتعطل الخدمات حسب PRD الأول.
8. **تطبيق في بيئة التشغيل:** أخذ نسخة من قيمة الإعداد السابقة، إعادة تشغيل/إنشاء الخدمات التي تقرؤها، والتحقق من القيمة الفعلية لجميع النسخ. لا طباعة secrets.env.
9. **تراجع:** إعادة قائمة الإعداد السابقة أو تعطيل تحسين الترتيب عند تراجع الجودة. لا حذف corpus أو vectors أو DB للتراجع عن تفعيل مصدر.

### المقاييس وبوابة النجاح

- 100% نجاح لاختبارات الأهلية والعقد والملفات المفقودة بمصادر fixtures ثابتة.
- مجموعة مرجعية مراجعة تضم على الأقل 10 أسئلة بدليل مناسب من islamqa و10 من binbaz و10 حالات تداخل/سلبية. يُثبت وجود الدليل قبل تقييم البحث؛ لا تُختلق أسئلة بدعوى أن مصدرًا يغطيها.
- Recall@8 للأدلة المرجعية ≥95% لكل مجموعة مصدر على حدة كهدف إصدار؛ يُذكر حجم العينة والعدد الصحيح، ولا تُحسّن النسبة بإزالة الحالات الصعبة بعد مشاهدة النتائج.
- صفر استشهاد بمصدر غير مسترجع أو معطل، وصفر ادعاء أن الاتصال بـMCP وحده يعني جاهزية المصدر.
- جودة الإجابة والسلامة والمهلة من PRD الأول لا تتراجع. لا يستبدل هذا القياس التحقق من دعم الجمل بالمراجع.
- تُعرض نسب التغطية والاسترجاع والاستشهاد لكل مصدر للتشخيص، **دون هدف 50/50**. إذا استمر ظهور ابن باز غالبًا مع أهلية وتغطية سليمة ونتائج مرجعية ناجحة، فهذا لا يكفي لاعتباره عطلًا.

ضع الوثيقة في:

```text

```

جذر المشروع هو المجلد الذي يحتوي `frontend/package.json` و`backend/pyproject.toml`. أضف رابطًا إلى هذه الوثيقة من `KNW-02-approved-sources-ingestion.md` ومن `docs/domains/knowledge/README.md` دون استبدال الوثائق الأصلية. يوجد ملف تسليم مستقل: `CLAUDE-SOURCE-COVERAGE-HANDOFF.md`.

ترتيب العمل مع PRD الأول: توحيد التشخيص والأخطاء أولًا، ثم إصلاح أهلية المصادر والجاهزية، ثم قياس الاسترجاع وتحسينه فقط إذا لزم، ثم تشغيل قبول الوثيقتين. لا ينشئ المطور محللين مختلفين للمصادر أو نظامي retries أو عتبتي ملاءمة متعارضتين.

تقرير التنفيذ النهائي في `docs/engineering/implementation/KNW-02-source-coverage-report.md` يجب أن يحتوي: القيمة الفعلية قبل/بعد دون أسرار، أعداد المقاطع والمتجهات لكل لغة، مكان MCP الفعلي أو سبب عدم التحقق منه، نتائج S01–S20، Recall@8 وجودة الإجابة، قائمة الملفات المعدلة، وما تم اختباره محليًا أو حيًا. لا يُعلن إصلاح الإنتاج بناءً على تعديل config أو نجاح `tools/list` وحدهما.

**خلاصة التشخيص:** الأرشيف يثبت أن islamqa مستبعد افتراضيًا من البحث وتجهيز المتجهات الدوري، رغم وجود مسار استيراده. الإصلاح المحدد هو توحيد السياسة وتطبيق الإعداد الفعلي وتجهيز البيانات وقياس وصول الأدلة، مع عدم فرض تنوع شكلي على الجواب. تحديد حالة الإنتاج ونجاح الإصلاح فيها يبقيان اختبارًا مطلوبًا أثناء التنفيذ.
