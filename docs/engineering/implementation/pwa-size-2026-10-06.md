# What takes Rafeeq's data and storage (measured 2026-10-06)

Evidence for PLT-11, PLT-12 and PLT-15. Measured against the live site (https://rafeeq.nan.sa, main at b89b760) and a local `vite build` of the same commit. Read-only requests only.

## Method

- Precache: parsed the manifest inside `dist/sw.js` and the live `/sw.js`; raw and gzip sizes per file.
- Real session: headless Chromium (Playwright, fresh profile, device onboarded in Arabic): `/` → reload → `/learn/lesson/u01-l3` → `/learn/lesson/u01-l6` (video played muted 30 s) → `/discover/quran`. Bytes on the wire per step from CDP `Network.loadingFinished.encodedDataLength`; storage from `navigator.storage.estimate()` and by walking Cache Storage. Caveat: open-source Chromium cannot decode H.264, so the lesson videos did not actually play in this run; their sizes below come from `Content-Length`.
- Media: `HEAD` (Content-Length) on every file in `content/discover/recitations.json` and 30 Quranpedia verse files; library sizes from the `size` field in `content/discover/library.json`.
- Headers: `curl -I` on the public URL and on the web container at `127.0.0.1:5380`.

### Headers: everything is `no-store` in production

The public response for `/assets/*`, `/fonts/*`, `/brand/*`, `/sw.js` and `/api/*` carries two `Cache-Control` headers: the container's own (`public, max-age=31536000, immutable` for hashed assets and fonts) plus `no-store, no-cache, must-revalidate` added by the host router. The container alone (`127.0.0.1:5380`) sends only the correct one. Browsers combine them and `no-store` wins, so nothing outside the service-worker precache is kept between visits. Fixing it requires a change to the host router configuration, which is outside this repo. PLT-11 R1 adds a deploy check that fails while the header is there.

## Conclusion

The ~200 MB figure is not confirmed (device and screen asked of the owner). The app shell is ~2 MB. The most likely source is streamed media: one play of Al-Baqarah from the IslamHouse recitation is a single 207 MB file, which the browser buffers and keeps for 30 days. The second cause is the `no-store` header, which re-downloads 0.5–0.75 MB on every open.

The app alone does not reach 50 MB. The only thing on the device that size is the first unit downloaded from the download centre (its videos), which the learner chooses; the figure matches it to the tenth of a MiB. Not confirmed on the owner's device. Two other readings of a «site size» remain possible (not measured): Chrome and Safari group site data by registrable domain (`nan.sa`, shared with every other app on that domain), and a played video can stay in the browser's HTTP cache (not counted in `storage.estimate`).

Found on the way: Workbox 7 precaches one file after another; on production the worker took ~40 s to install (124 files). Until it is active, every page load fetches the whole shell again (`no-store`), ~0.8 MB each, and the app does not open offline. Fix: `frontend/src/sw/precache-fill.ts` fetches the precache six at a time alongside Workbox (local, 250 ms per response, no-store: 40 s → 14–19 s over HTTP/1.1; each file still fetched once). The 512 px manifest icon (139 KB) left the precache. Same walk on a local build: wire 5.64 → 4.44 MB; precache 1.91 → 1.77 MB. Site storage after the walk 2.25 → 3.86 MB, because the worker now takes over early enough in the first visit to keep the fonts (0.32 MB, kept on the second visit before) and Chrome adds compiled-code data to scripts served from Cache Storage.

**Owner decision 2026-10-10 (PLT-12 R2): videos are never part of a unit download.** Local build + local backend, headless Chromium, ar: unit u01 now 3,923,790 bytes in the catalogue; downloaded, `rafeeq-downloads` holds 28 files, 3.73 MiB (text, pictures, Al-Fatiha tafsir audio), and `storage.estimate` grows by 4.6 MiB; no video request during the download. Each video is its own opt-in item (ar wudu 21.0 MiB, prayer 25.3 MiB; en wudu 47.2 MB). In the lesson, the video streams on tap (playing after ~1.1–1.7 s locally) and nothing of it is fetched before.
